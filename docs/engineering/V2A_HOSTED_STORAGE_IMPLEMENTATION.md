# Money Moves — Hosted Storage Migration — Implementation Report

**Status:** Candidate implementation. Not self-accepted. Per the standard Money
Moves handoff model, a separate, independent pass must review and accept this
before `IMPLEMENTATION_STATUS.md` is updated.

**Base revision:** `4c0eb5b649a3b30e9d03c978c9b6a66f1623a408` (v2a-phase3c-cross-tab-accepted)

## 1. Scope

Moved the encrypted vault's storage address from `localStorage` to a Postgres row
hosted by Supabase, reachable directly from the browser via Supabase's own
RLS-enforced REST API, with Google sign-in (Supabase Auth) as the account layer.
The client-side encryption boundary — key derivation, AES-GCM encrypt/decrypt,
non-extractable `CryptoKey` — is untouched. Concurrency-safety authority moved from
the client-side Web Lock + persisted lease to a single atomic conditional write
(`UPDATE ... WHERE generation = $expected`), per the locked product decision.

Excluded, as specified: Plaid Sandbox/Link/sync, server-side querying or analytics
on transaction data, reimbursement UI, multi-device conflict UX beyond what the
generic banner already provides.

## 3. Deviations from the prompt, with rationale

The prompt was detailed and prescriptive. Several implementation choices genuinely
depart from a literal reading of it. Flagging all of them here rather than letting
an independent reviewer discover them unannounced.

### 3.1 No custom Vercel API layer

The prompt frames Vercel as hosting "a server-side conditional write." What's built
instead: the atomic conditional write is a direct call from `hostedVaultStorage.js`
to Supabase's own PostgREST layer (`supabase.from('vaults').update(...).eq('user_id', uid).eq('generation', expected)`),
authorized by the user's own session JWT and enforced by Row-Level Security. No
custom backend code ever sees the request. Vercel's role narrows to exactly what
`start.py` does today: serve static files. This was flagged and approved
mid-session (see conversation) — restated here for the written record. It is the
"least tech debt" reading of the product owner's own stated rationale: zero new
trusted-server surface for this phase, versus writing and maintaining custom API
routes that would do exactly what PostgREST already does.

### 3.2 No server-side temp-row / two-phase write

The old `localStorage` design wrote a temp record, decrypted it to verify integrity,
then promoted it to active — necessary because `localStorage` has no native
transactionality. Postgres's own `UPDATE` is already atomic and durable, so nothing
server-side plays the temp record's role. What replaces it: the client decrypts its
own freshly-encrypted ciphertext locally, before ever sending it (see
`writeCoordinated` in `js/vault.js`), catching a broken encryption result before
wasting a network round trip. No temp-record equivalent exists in
`supabase/migrations/0001_hosted_vault.sql`.

### 3.3 Idempotency-nonce reconciliation for the ambiguous-write case

This is the mechanism, not just a test, for "response lost but the write actually
committed" — the case the prompt named as having no `localStorage` analog. Every
write's target generation is a client-generated random nonce. On any ambiguous
failure (thrown/network error, or an insert's unique-violation error), the client
issues one follow-up read and compares the row's current generation against the
nonce it was attempting: a match proves its own write landed (report success, no
data loss, no user-visible retry); the old expected generation still present means
the write never landed (safe to retry); anything else is a genuine conflict from a
different writer. Implemented in `performWrite`/`reconcile` in
`js/services/hostedVaultStorage.js`, exercised directly in
`test/hosted-vault-storage.test.js`.

### 3.4 Persisted write-lease retired for the hosted path

`V2_VAULT_WRITE_LEASE_KEY` protected against exactly the non-atomic
read-then-write sequence that the atomic conditional write makes structurally
impossible. Keeping a redundant, purely local, easily-stale lease around added
complexity without adding safety, so it's gone — removed from
`js/domain/constants.js` along with the other two retired keys. The Web Lock stays,
demoted to a same-device coalescing optimization exactly as the product owner's
decision specified.

### 3.5 BroadcastChannel added (not requested)

Once the vault leaves `localStorage` entirely, the native `storage` event that gave
other same-device tabs an early "someone else just saved" warning never fires
again — nothing local changes on a hosted write. Without a replacement, the
existing two-tab conflict banner would silently regress from appearing immediately
to appearing only after a tab's own save fails. Added a same-device
`BroadcastChannel` announcement on every successful hosted write
(`subscribeToRemoteWrites`/`announceRemoteWrite` in `hostedVaultStorage.js`) purely
to preserve that existing UX. It is advisory only, exactly like the event it
replaces — the authoritative check remains the conditional write itself.

### 3.6 `resetVault` repurposed, not implemented as data erasure

The existing button read "Erase the encrypted local vault from this browser?" and
called `stateService.clearCurrentVault()`. Under this design there is nothing local
left to erase, and implementing hosted-vault deletion was not asked for and is a
materially more consequential, irreversible action than this phase's scope
suggests. Rather than ship a button that visibly claims to erase data while
silently doing nothing, it now signs out of the browser (revokes the local
session, does not touch the hosted row) with copy that says exactly that. Actual
hosted-vault deletion remains unimplemented and would need its own explicit design
and product-owner sign-off.

### 3.7 Automatic V1-to-V2 storage migration is removed, not adapted — and its entire test file is deleted

This is the largest deviation and deserves to be stated plainly rather than buried
in a test-file diffstat. Before this phase, `unlock()` would transparently detect a
V1-only browser, migrate it into a fresh V2 vault, and keep the V1 ciphertext as a
recovery copy — this was the mechanism `test/vault-migration.test.js`'s ~15 tests
exercised almost in their entirety. That mechanism is fundamentally a "local data
blends into local storage" design; it cannot be preserved under a per-account
hosted model without violating the product owner's explicit "discarded... no
import, no dual-write" decision, so it isn't preserved. `js/vault.js`'s hosted read
path (`readVaultRecord`) no longer falls back to V1 keys at all.

What remains, and is tested in the new `test/v1-local-recovery.test.js`: V1
ciphertext is still never deleted by any V2/hosted operation, and
`readLocalV1Record()`/`readLegacyState()` remain functional, callable primitives —
just no longer wired into the automatic boot flow. `test/vault-migration.test.js`
was deleted rather than adapted because its premise no longer exists in this
design; a mechanical port would have meant testing a mechanism that isn't there.

`test/vault-coordination.test.js` was deleted for the parallel reason given in
§3.4: the persisted lease and temp-vault crash matrix it tested (100-race lock
stress, lease expiry, temp-record recovery states) are retired mechanisms. Its
properties are re-verified in `test/hosted-vault-storage.test.js` against the new
mechanism — same acceptance bar (no double success, generic conflict, full
rollback, no double-application on retry), different implementation underneath.

### 3.8 Vendored, not CDN-loaded, and not bundled with a build step

`@supabase/supabase-js` ships with bare-specifier imports to sibling packages that
a browser cannot resolve without either a bundler or a CDN's own pre-bundling. This
project deliberately has no bundler. Rather than add one (real scope creep) or take
a live runtime dependency on a third-party CDN (the app currently makes zero
external script requests), the package was bundled once with `esbuild --platform=browser`
into a single self-contained file, `js/vendor/supabase-js/index.mjs`, committed like
any other file. Verified in a real browser tab: loads with zero console errors, full
auth/query API surface present, no reliance on `Buffer`/`process` globals a real
browser lacks. Re-bundling on a version bump is `pnpm run vendor:supabase`.

## 4. Requirements implemented

Mapped to the phase spec's numbered "Required outcomes":

1. **Auth before any read/write** — `hostedVaultStorage.js` resolves the current
   session on every call and throws `HostedVaultAuthRequiredError` (mapped to
   `VaultAuthRequiredError`, code `VAULT_AUTH_REQUIRED`) if none exists; `js/app.js`
   routes to the sign-in panel on this specific error rather than a generic failure.
2. **Encrypted blob storage, one row per user** — `vaults` table, `user_id` primary
   key, `blob jsonb`, never queried or parsed server-side.
3. **Key handling unchanged, verified explicitly** — see §3 of the earlier
   investigation report (carried forward): `deriveKey()` produces a
   non-extractable `CryptoKey`; nothing in this phase touches `encryptState`/
   `decryptState`; the key is never serialized, logged, or included in any network
   payload. Re-confirmed by code review of the final `js/vault.js`.
4. **Concurrency preserved, re-tested for network latency, not assumed safe by
   analogy** — see §3.3; `test/hosted-vault-storage.test.js` includes a 100-race
   stress test, the three named network-failure scenarios, and an explicit
   cross-device test using two independently-driven fake clients sharing one row
   (no Web Lock coordination possible or assumed between them).
5. **Plaid token boundary built, not populated** — `plaid_secrets` table exists
   with RLS enabled and, deliberately, zero policies granted to the
   `authenticated`/`anon` roles — default-deny from the browser in every case,
   unlike `vaults`. Nothing in this phase's code references the table.
6. **TLS enforced** — inherent to Supabase's and Vercel's hosted endpoints; nothing
   in this codebase can weaken it. Not independently verifiable without a live
   deployment (see §6).
7. **Row-Level Security enabled on both tables** — in the migration; not yet
   verified against a live project (see §6).

## 7. Known limitations — read before accepting

**Nothing in this candidate has been tested against a real Supabase project.**
There is no live Supabase account, no live Google OAuth client, and no live Vercel
deployment associated with this work — creating those requires a human with
account-creation authority, per this agent's own operating constraints, and
`docs/engineering/HOSTED_STORAGE_SETUP.md` exists specifically to hand that off.
Every test in `test/hosted-vault-storage.test.js` runs against
`test/hostedVaultFake.js`, a hand-built double of exactly the two Supabase call
shapes this code uses (`select().eq().maybeSingle()`, `insert().select()`,
`update().eq().eq().select()`). It was built to mirror PostgREST's real conditional-
update semantics faithfully (row-count as the success signal, matching WHERE
clauses failing closed), but it is not PostgREST, and requirement 6 (TLS) and the
"RLS actually enforces `auth.uid() = user_id`" half of requirement 7 cannot be
verified by anything in this repository — only by running the migration against a
real project and testing from two real authenticated sessions.

Two smaller open items, consistent with the ones Phase 3C left open for the same
reason: the sign-in button's error path when OAuth genuinely fails (e.g., the
user's Google session is invalid, or the redirect is misconfigured) has not been
exercised against a real IdP — only confirmed not to crash against a nonexistent
project. And `js/vendor/supabase-js/index.mjs` is a point-in-time bundle; nothing
automatically flags when the pinned version falls behind upstream security fixes.
